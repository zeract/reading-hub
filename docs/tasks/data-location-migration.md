# 任务：无损接管历史本地数据目录

状态：完成

## 目标与范围

- 用户可观察的预期行为：升级后的应用在启动服务、同步或历史维护前，识别固定的历史 Reading Hub 数据目录；当当前库不存在或为空且存在一份可验证的历史库时，创建一致性备份并安全接管来源、卡片、阅读状态、收藏、同步进度和改写记录。旧目录不会被删除。
- 不包含：任意磁盘扫描、自动合并两份非空数据库、复制 Chrome Cookie、导出 Keychain 凭据，或新增远程自动更新服务。
- 已确认的决策、授权及限制：只检查 `reading-hub` 与历史 `Reading Hub`、`Electron` 根目录；SQLite 迁移必须使用 backup API 覆盖 WAL。即使是 `Electron` 根，也只接受其中能通过 Reading Hub 验证的 `reading-hub.sqlite`。应用不迁移 Chromium 登录会话、Cookie 或 Keychain 凭据；升级后如知乎会话已失效，用户重新登录即可，不影响内容库接管。

## 根因与契约

- 已验证证据（文件/测试/样本，不存私密正文）：当前启动固定使用 `appData/reading-hub/reading-hub.sqlite`；最早未品牌化开发版会使用 Electron 默认的 `appData/Electron/reading-hub.sqlite`，历史品牌预览可能使用 `appData/Reading Hub/reading-hub.sqlite`。现有 schema 迁移仅作用于已打开的活库。SQLite 已启用 WAL，直接复制主文件会遗漏已提交日志。
- 受影响的数据归属、接口、失败/恢复规则：解析器在 `createApplicationServices()` 前运行。历史库先只读验证、备份到当前目录的 `backups/`，在暂存文件上验证后再原子替换当前数据库。当前库与历史库同时有任意用户状态时不选择或覆盖任一方；损坏、未来 schema、来源指纹不一致或接管失败也不创建空库掩盖问题。
- 持久化或协议变更的兼容与回退方式：新增只含来源位置哈希、schema、计数、指纹、阶段和时间的迁移记录，不含正文、Cookie 或密钥；v17 另在目标 SQLite 内保存来源指纹与位置哈希。两者与保留的历史库都匹配时，才承认迁移已完成。原历史目录和升级前快照均保留；schema 的逐版本事务与未来版本拒绝保持不变。
- 长期设计文档链接：[架构](../architecture.md)
